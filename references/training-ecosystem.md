# Training ecosystem source brief

Verified 2026-09-28 against primary project documentation and the exact supplied paper. This is curriculum research, not an installed or tested software environment. Unversioned documentation can drift; select and lock a compatible release only when the first environment is built.

## Exact requested paper

The link is **Kimi K3: Open Frontier Intelligence**, Kimi Team, submitted July 27, 2026; latest displayed revision v2 August 7, 2026. The abstract describes a 2.8T-parameter MoE with 104B active parameters, native vision and million-token context. These are author-reported claims, not independently reproduced here. [arXiv record](https://arxiv.org/abs/2607.24653)

The report covers architecture (Kimi Delta Attention, Attention Residuals, Stable LatentMoE), pretraining data, scaling laws, optimizer/training recipe, context extension, post-training, infrastructure and evaluation. It is a good longitudinal reading case: return to each section after learning the corresponding fundamentals. Treat frontier-scale reproduction as out of scope. Suggested advanced questions: how does its design alter memory/computation; which evidence supports each claimed gain; which details are missing for reproduction? [Full text v2](https://arxiv.org/html/2607.24653v2)

## Library roles and learning order

1. **Foundations before wrappers (curriculum recommendation):** Python/tensor manipulation, matrix calculus and probability; autograd and optimizers; tokenization; next-token cross entropy; causal attention; a small decoder-only model; training/validation splits; checkpoint/resume. Learner should trace tokens → logits → loss → gradients → update before treating any trainer as understood.
2. **Transformers + Datasets + TRL:** practical model/tokenizer loading, data transformation, configurations and trainers. TRL's current taxonomy lists SFT/DPO/KTO as offline methods, RewardTrainer for reward modeling, GRPO/RLOO online methods, and DistillationTrainer; several others are experimental. Do not turn the trainer catalogue into mandatory coursework. [TRL overview](https://huggingface.co/docs/trl/index)
3. **SFT:** inspect language-modeling vs prompt-completion examples and conversational templates; identify exactly which tokens incur loss. Current docs expose packing and assistant-only loss. Assessment: independently explain masks, one-token prediction alignment, padding, EOS and truncation; compare held-out loss and generated samples. Current default loss path is `chunked_nll`, not necessarily older tutorial defaults. (October 27 recheck: in TRL v1.16.0 the default `loss_type` is `nll`, and `chunked_nll` is a deprecated alias.) [SFT docs](https://huggingface.co/docs/trl/sft_trainer)
4. **PEFT/LoRA then QLoRA:** first learn trainable low-rank updates and frozen base parameters; next examine quantization and memory tradeoffs. PEFT documents quantized training preparation and QLoRA-style targeting of all linear layers. Quantized weights do not eliminate activations, optimizer/adaptor state or numerical issues. Preserve the base model revision, tokenizer and adapter configuration with every adapter artifact. [PEFT](https://huggingface.co/docs/peft/index), [quantization guide](https://huggingface.co/docs/peft/developer_guides/quantization)
5. **DPO and reward modeling:** connect paper-level knowledge to actual chosen/rejected data, sequence log probabilities, reference policy and controlled comparisons. DPO's default reference is the initial policy when none is provided; precomputing reference log probabilities can reduce training memory. Explicitly record beta, length policy and objective variant. Current docs warn padding-free DPO temporarily falls back to padding after a refactor. [DPO](https://huggingface.co/docs/trl/dpo_trainer)
6. **Reward modeling before online RL:** train a preference scorer and evaluate held-out preference accuracy, margins and failure slices; study reward hacking. Current RewardTrainer uses a one-output sequence classifier and documents Bradley–Terry reward offset indeterminacy. Reward score increase alone is insufficient evidence of useful behavior. [Reward docs](https://huggingface.co/docs/trl/reward_trainer)
7. **PPO concepts → small GRPO experiment:** teach trajectories, policy gradients, baseline/advantage, importance ratios, clipping and KL. Then use a verifiable task with carefully tested reward functions. GRPO diagnostics include zero-variance reward groups, truncated completions, entropy and train/inference log-probability mismatch; current beta defaults to zero, so KL is absent unless explicitly enabled. Read the actual version's objective rather than assuming it equals the original paper. [GRPO](https://huggingface.co/docs/trl/grpo_trainer)
8. **Distributed systems after single-device correctness:** build a parameter/gradient/optimizer/activation memory budget, profile throughput, then learn accumulation, mixed precision, DDP and sharding. Accelerate bridges device/distributed execution; FSDP and DeepSpeed differ in configuration, precision and checkpoint handling. The cited comparison explicitly scopes itself to single-node multi-GPU use; do not infer multi-node readiness from it. Add FSDP1/FSDP2 distinction before selecting examples. [Accelerate](https://huggingface.co/docs/accelerate/index), [FSDP vs DeepSpeed](https://huggingface.co/docs/accelerate/concept_guides/fsdp_and_deepspeed)
9. **Evaluation throughout:** use held-out loss, fixed generation samples and task-specific tests from the start, then the LM Evaluation Harness for reproducible external tasks. Pin task configuration, model/tokenizer revisions, prompt formatting, generation settings and seeds; keep training data separate from benchmark/test examples. Report uncertainty, cost and failure cases, not only a leaderboard number. [Harness primary repository](https://github.com/EleutherAI/lm-evaluation-harness)

## Version and practical constraints

- Current unversioned TRL overview does not list PPO in its trainer taxonomy. Its unversioned PPO URL returned no useful content in this check; a historical v0.11.4 page is accessible. This does **not** establish removal from every package/version. Teach PPO conceptually and select a verified implementation later; do not combine historical PPO snippets with current APIs. [Historical PPO docs](https://huggingface.co/docs/trl/v0.11.4/ppo_trainer)
- Freeze Python, PyTorch, Transformers, TRL, Datasets, PEFT, Accelerate, optional bitsandbytes/vLLM/DeepSpeed, CUDA/driver, model/dataset revisions and exact configs. Smoke-test save/reload and resume before spending a run budget. This is a proposed reproducibility requirement, not a verified compatibility matrix.
- No hardware availability or budget was verified. Start with CPU/small-device tensor exercises and tiny models. Choose CUDA-specific, quantized or multi-GPU labs only after actual GPU, VRAM and rental budget are known. No frontier-scale hardware purchase is implied.
- Keep MoE, multimodal training, long-context kernels, agentic RL, distillation and advanced parallelism as later electives/readings until the core train–debug–evaluate loop is demonstrated.
- Suggested artifacts are a data card, run manifest, learning curves, memory/throughput measurement, checkpoint reload proof, evaluation report and learner explanation. None should be pre-completed by the teacher.
